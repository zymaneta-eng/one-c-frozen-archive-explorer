## 🇺🇦 1. Бізнес-контекст та регуляторні вимоги в Україні

### Проблема: Санкції проти російського ПЗ та вимоги Податкового кодексу
Згідно з указами Президента України та рішеннями Ради національної безпеки і оборони (РНБО) України, щодо розробників і правовласників російських систем («1С», «BAS» тощо) запроваджено обмежувальні заходи (санкції). Українські підприємства планово виводять ці системи з експлуатації та мігрують на сучасні ERP/CRM платформи.

Водночас **пункт 44.3 статті 44 Податкового кодексу України (п. 44.3 ст. 44 ПКУ)** зобов'язує платників податків забезпечити збереження первинних документів, облікових регістрів та фінзвітності:
* **Не менше 1 825 днів (5 років)** — для первинних документів, пов'язаних з податковою звітністю;
* **Не менше 2 555 днів (7 років)** — для документів щодо контрольованих операцій (трансфертне ціноутворення, ст. 39 ПКУ).

### Практична дилема фінансової служби:
1. **Не можна тримати 1С увімкненою:** Продовження оплати ліцензій, супроводу ІТС або підтримка вразливих застарілих Windows-серверів порушує корпоративні політики безпеки та санкційний комплаєнс.
2. **Не можна видалити базу:** Відсутність доступу до первинних документів під час перевірки ДПС або аудиту загрожує невизнанням витрат, зняттям податкового кредиту та штрафними санкціями.
3. **Хмарні SaaS — надлишкові витрати:** Оплачувати щомісячні тарифи за важку хмарну інфраструктуру лише заради пасивного архіву 3–5-річної давнини є економічно неефективним.

## 🏛️ 2. Концепція дворівневого зберігання (Two-Tier Preservation Model)

Перетворення даних у CSV/DuckDB не замінює юридичні оригінали документів. Саме тому проект базується на інженерно вивіреній дворівневій моделі консервації:

```
┌────────────────────────────────────────────────────────────────────────┐
│                        КОНСЕРВАЦІЯ БАЗИ 1С / BAS                       │
└──────────────────┬──────────────────────────────────┬──────────────────┘
                   │                                  │
                   ▼                                  ▼
┌─────────────────────────────────────┐    ┌─────────────────────────────┐
│   РІВЕНЬ 1. ХОЛОДНИЙ ОРИГІНАЛ       │    │  РІВЕНЬ 2. ДЕПОЗИТАРІЙ      │
│   (Cold Tier — Юридичний архів)     │    │  (Explorer Tier — Пошук)    │
│                                     │    │                             │
│ • Повний дамп бази (*.1CD, *.bak)   │    │ • DuckDB колоночні вибірки  │
│ • Архіви КЕП-підписів (Вчасно/MEDoc)│    │ • SQLite FTS5 BM25 індекс   │
│ • Незмінні RAW JSON/XML вивантаження│    │ • Швидкий веб-інтерфейс     │
│ • Збереження на захищеному носії    │    │ • Акти звірки та специфікації│
│                                     │    │ • Субсекундний пошук < 30 мс│
│ 🎯 Мета: Юридична недоторканність   │    │ 🎯 Мета: Щоденний комфорт   │
└─────────────────────────────────────┘    └─────────────────────────────┘
```

1. **Холодний рівень (Cold Tier):** Повний образ файлової бази або SQL-дамп (`*.1CD`, `*.bak`) разом з архівами електронних первинних документів та квитанцій з КЕП (з M.E.Doc, Вчасно, Сота) зберігається на захищеному холодному носії підприємства як первинний юридичний еталон.
2. **Операційний шар (Frozen Archive Explorer):** Легковажний локальний депозитарій, який підхоплює нормалізовані реєстри, забезпечує швидкий повнотекстовий пошук за реквізитами, відображає товарні специфікації, перевіряє розрахунки та формує вивантаження без увімкнення 1С.

## 🗄️ 5. Фінансова модель даних та правила розрахунків

### Збереження грошових сум у цілих копійках (`BIGINT`)
Для виключення похибок двійкового округлення чисел із плаваючою комою (`float drift`) усі розрахунки та зберігання в базі ведуться виключно в цілих копійках:
* `1 000,50 ₴` зберігається в базі як ціле число `100050` копійок.
* `62 096 718,00 ₴` зберігається як `6209671800` копійок.
* При відображенні сума форматується з тонким розділювачем тисяч: `62 096 718,00 ₴`.
* Для друкованих форм і картки документа сума конвертується в офіційну суму прописом українською мовою:  
  *Приклад: `62 616,00 ₴` &rarr; «Шістдесят дві тисячі шістсот шістнадцять гривень 00 копійок».*

### Багатоорганізаційний облік (Multi-Company)
Депозитарій дозволяє вести облік декількох пов'язаних юридичних осіб компанії:
* **ТОВ (Платник ПДВ 20%):** автоматичний розрахунок бази оподаткування, виділення суми ПДВ та перевірка математичної рівності: `База + ПДВ = Разом`.
* **ФОП (Єдиний податок, Спрощена система):** автоматична позначка `Без ПДВ`.

### Підтримувані типи операцій та напрямки:
* **Напрямок «Реалізація / Продаж» (OUT):**
  1. **Видаткова накладна (РН-)** — відвантаження товарно-матеріальних цінностей;
  2. **Акт виконаних робіт / наданих послуг (АКТ-)** — підтвердження реалізованих послуг;
  3. **Платіжна інструкція (ПІ-)** — вхідні безготівкові оплати від клієнтів (Кредит у взаєморозрахунках);
  4. **Рахунок на оплату (СФ-)** — замовлення та рахунки-фактури.
* **Напрямок «Купівля / Витрати» (IN):**
  1. **Прибуткова накладна (ПНк-)** — оприбуткування товарів, сировини та обладнання від постачальників;
  2. **Акт отриманих послуг (АктВх-)** — оренди, комунальні послуги, підряди та юридичний супровід;
  3. **Платіжна інструкція вихідна (ПІв-)** — оплати постачальникам (Дебет у взаєморозрахунках).

## 🏛️ 6. Корпоративний комплаєнс: 5 зон надійності для ДПС та аудиту

1. **Податковий контур (ПДВ / ЄРНН):**
   * Зв'язування кожної операції з Податковою накладною (ПН/РК) та статусом реєстрації в ЄРНН.
   * Фіксація дати реєстрації та підтвердження отримання **Квитанції № 2 від ДПС**.
   * Швидкі фільтри: `Всі статуси`, `Зареєстровано в ЄРНН`, `Не зареєстровано`, `Без ПДВ`.
2. **Вхідна первинка від постачальників (Витрати):**
   * Повноцінний облік витратної частини для захисту собівартості та податку на прибуток при податкових перевірках за п. 44.3 ст. 44 ПКУ.
   * Фільтрація за напрямком: `Всі напрямки` / `↗ Продаж (Реалізація)` / `↙ Купівля (Витрати)`.
3. **Юридичний статус та КЕП (Вчасно / M.E.Doc / Сота):**
   * Фіксація форми первинного документа: `Електронна (КЕП)` чи `Паперова (оригінал)`.
   * Збереження сервісу ЕДО (`Вчасно`, `M.E.Doc`, `Сота`), сертифіката підписанта та криптографічного хешу цифрового підпису `.p7s` (SHA-256) згідно з вимогами Закону № 2155-VIII.
4. **Рольовий доступ (Role-Based Access Control):**
   * Перемикач профілів у верхній панелі без необхідності складного адміністрування:
     * 👑 **Головний бухгалтер:** необмежений доступ до всіх юросіб (ТОВ + ФОП), звітів та бекапів;
     * 🏢 **Бухгалтер ТОВ:** автоматична фільтрація виключно за юридичною особою ТОВ "Ареонікс Діджитал";
     * 👤 **Бухгалтер ФОП:** автоматична фільтрація виключно за підприємцем ФОП "Ареонікс-Сервіс";
     * 🔍 **Аудитор / ДПС:** режим «Тільки читання» (Read-only), пряме завантаження бази заблоковане.
5. **Аварійне відновлення (Cold Storage Disaster Recovery ZIP):**
   * Експорт в один клік архіву `Frozen_Archive_ColdBackup_YYYYMMDD.zip`, що містить:
     * `archive_vault.duckdb` — повне колоночне сховище первинки та специфікацій;
     * `archive_index.db` — повнотекстовий індекс SQLite FTS5;
     * `archive_manifest.json` — криптографічні хеші SHA-256;
     * `README_RESTORE.txt` — автономна інструкція з розгортання та перевірки цілісності.

## 🛡️ 7. Криптографічний контроль цілісності даних (SHA-256 Manifest)

> **Інженерне уточнення:** Даний механізм не є апаратним WORM-носієм (Write Once, Read Many). Це криптографічний протокол захисту даних від випадкових змін, пошкодження файлової системи або несанкціонованої модифікації.

* При кожній процедурі консервації формується `archive_manifest.json`, який фіксує контрольні суми SHA-256 для файлу бази `archive_vault.duckdb` та Parquet-файлів.
* У веб-інтерфейсі доступне модальне вікно перевірки, яке в реальному часі перераховує хеш і звіряє його з маніфестом.
* При аудиті контрольна сума дозволяє довести, що база після завершення вивантаження залишалася незмінною.

## 📋 7. Покроковий регламент консервації

Для безпечного виведення 1С / BAS з експлуатації застосовується 5-етапний регламент:

1. **Створення холодного бекапу:** Вивантаження повної копії бази (`*.1CD`, `*.bak`) на зовнішній ізольований носій разом з архівами електронних накладних з КЕП (Вчасно/M.E.Doc).
2. **Експорт реєстрів у погодженому форматі:** Формування таблиць довідника контрагентів, журналу первинних документів та рядків номенклатури.
3. **Консервація та індексація:** Запуск імпортера для завантаження в DuckDB, побудови Parquet-снапшотів та індексації у SQLite FTS5:
   ```bash
   python -m one_c_frozen_archive_explorer.freeze_importer
   ```
4. **Сверка контрольних підсумків (Reconciliation):** Перевірка кількості перенесених документів та підсумкових сум оборотів до і після консервації:
   ```bash
   python -c "from one_c_frozen_archive_explorer.search_engine import SearchEngine; e = SearchEngine(); s = e.get_archive_stats(); print(f'Перенесено документів: {s.total_documents}, Підтверджений оборот: {s.formatted_total}')"
   ```
5. **Вимкнення серверів 1С:** Зупинка серверів, вимкнення віртуальних машин, закриття договорів супроводу ІТС. Доступ до історії надається через локальний інтерфейс.

## 🚀 8. Встановлення та швидкий старт вітрини

### Системні вимоги:
* **Python:** версія 3.10 або новіша
* **Операційна система:** Windows 10/11, Windows Server, Linux (Ubuntu, Debian, RHEL) або macOS
* **Мережа:** Підключення до Інтернету не потрібне для роботи інтерфейсу (локальний запуск)

### 1. Клонування репозиторію вітрини та встановлення
```bash
git clone https://github.com/zymaneta-eng/one-c-frozen-archive-explorer.git
cd one-c-frozen-archive-explorer
pip install -e .
```

### 2. Генерація тестового верифікованого архіву (100 компаній, 1 000 документів)
Для демонстрації можливостей пошуку та звітів згенеруйте тестовий набір даних:
```bash
python -m one_c_frozen_archive_explorer.generator
```
Команда створить:
* 100 реалістичних українських контрагентів (ТОВ, ПП, ПрАТ з 8-значними ЄДРПОУ; ФОП з 10-значними ІПН);
* 1 000 первинних документів за 2021–2025 роки з номенклатурними специфікаціями;
* Файли сховища DuckDB, індекс SQLite FTS5 та Snappy Parquet снапшоти.

### 3. Запуск локального веб-інтерфейсу
```bash
python -m one_c_frozen_archive_explorer.server
```
Інтерфейс доступний у браузері за адресою: **`http://127.0.0.1:8020`**

| Тип операції | Обсяг вибірки | Час відповіді | Статус (< 50 мс) |

| **Пошук за номером документа** (`РН-00077`) | 1 000 документів | 1.6 – 24.0 мс | ✅ Виконано |
| **Пошук за назвою послуги чи номенклатури** | 1 000 документів | 2.1 – 29.5 мс | ✅ Виконано |
| **Миттєвий автокомпліт контрагентів** | 100 компаній | 4.2 – 8.5 мс | ✅ Виконано |
| **Розрахунок глобальних агрегатів і оборотів** | 1 000 документів | 3.8 – 6.2 мс | ✅ Виконано |

### Обсяг дискового простору та стиснення:
* **База даних DuckDB:** 4.01 МБ
* **Повнотекстовий індекс SQLite FTS5:** 0.49 МБ
* **Колоночні файли Snappy Parquet:** **0.12 МБ (123 КБ)**
* **Коефіцієнт стиснення:** понад **90%** у порівнянні з первинними текстовими/XML даними.
